# Render + Aiven MySQL Deployment Guide

Production deployment reference for the MaliciousBot / PARI + Nikhil fallback
application on **Render Free Web Service** with **Aiven MySQL** and
**MongoDB Atlas**.

---

## 1. Render Web Service settings

| Setting | Value |
|---|---|
| Service type | Web Service |
| Runtime | Python |
| Plan | Free |
| Root Directory | *leave blank* |
| Build Command | `./build.sh` |
| Start Command | `gunicorn MaliciousBot.wsgi:application` |
| Health check path | `/health` |
| Instance type | Free (512 MB RAM, 0.5 CPU) |

`start.bat` is Windows-only and must **not** be used on Render.

> **Executable bit:** `./build.sh` requires the file to be committed with mode
> `100755`. On Windows, commit it with `git update-index --chmod=+x build.sh`
> (after `git add build.sh`) so the mode is recorded. If the deploy instead
> fails with `Permission denied`, change the Build Command to `bash ./build.sh`,
> which does not depend on the mode bit.

> Render already runs `pip install -r requirements.txt` before the Build
> Command. The explicit install in `build.sh` is kept so the script is
> self-contained and safe to run manually; it is a fast no-op on Render.

Gunicorn is already configured for a single free instance. To reduce memory
pressure and avoid worker restarts during long deep-analysis runs, the start
command may be tuned to:

```
gunicorn MaliciousBot.wsgi:application --workers 1 --threads 4 --timeout 120 --bind 0.0.0.0:$PORT
```

## 3. Aiven SSL approach

The MySQL driver is **PyMySQL** (pure Python, no build toolchain needed on
Render). `MaliciousBot/__init__.py` registers it as `MySQLdb` before Django
opens any connection. `cryptography` is included because PyMySQL needs it for
MySQL 8 `caching_sha2_password` authentication.

A single helper, `MaliciousBot/db_config.py`, builds a single
`ssl.SSLContext` that is injected into `DATABASES['default']['OPTIONS']['ssl']`
and `DATABASES['guest_db']['OPTIONS']['ssl']`. Every dynamically registered
per-user database is cloned from the `default` connection, so it inherits
**identical** host, port, credentials and TLS settings. The raw admin
provisioning connection in `User/db_manager.ensure_mysql_database_exists()`
uses the same helper, so provisioning can never silently fall back to a
plaintext socket.

### Mode selection

`MYSQL_SSL_MODE` is resolved as follows:

| Situation | Effective mode | Result |
|---|---|---|
| `MYSQL_HOST` is `localhost` / `127.0.0.1` | `DISABLED` | No TLS kwargs added. Local development is unchanged. |
| Remote host, `MYSQL_SSL_CA` **not** set | `REQUIRED` | TLS negotiated, certificate **not** authenticated. |
| Remote host, `MYSQL_SSL_CA` set | `VERIFY_CA` | TLS + certificate chain validated against the Aiven CA. |
| `MYSQL_SSL_MODE` set explicitly | that value | Honoured and validated. |

`VERIFY_CA` and `VERIFY_IDENTITY` **fail fast** with `MySQLSSLConfigurationError`
if `MYSQL_SSL_CA` is missing or unreadable, so a misconfigured production
deployment stops instead of silently downgrading.

### Recommended production setup

Upload the Aiven CA through **Render → Service → Secret Files** and set:

```
MYSQL_SSL_MODE=VERIFY_CA
MYSQL_SSL_CA=/etc/secrets/aiven-ca.pem
```

`VERIFY_CA` is the least complex mode that both encrypts *and* authenticates the
Aiven server. `VERIFY_IDENTITY` additionally checks the hostname against the
certificate and can be used if Aiven's certificate SAN matches the service
hostname.

`charset=utf8mb4` and `init_command="SET sql_mode='STRICT_TRANS_TABLES'"` are
unchanged.

## 4. Database architecture

The per-user isolation architecture is preserved unchanged.

```
maliciousbot_core     ("default")  auth, sessions, admin, contenttypes, user_database_registry
maliciousbot_guest    ("guest_db") application tables, shared by anonymous visitors
maliciousbot_user_XXXXXX            application tables, one database per user
```

* `User.db_router.UserDatabaseRouter` keeps control tables in `default` and
  application tables in the request's database.
* `User.db_manager.ensure_user_database()` provisions the database, registers a
  Django connection alias, and migrates it on first use.
* `User.models.UserDatabaseRegistry` tracks the mapping in the core database.

## 5. Migration behaviour

`build.sh` runs, in order:

1. `pip install -r requirements.txt`
2. `python manage.py collectstatic --noinput`
3. `python manage.py migrate --noinput` — core database (`maliciousbot_core`)
4. `python manage.py migrate --database=guest_db --noinput` — guest database

Notes:

* No `--fake` or `--fake-initial` is used anywhere.
* No destructive operation (`flush`, `sqlflush`, `migrate zero`, dropped tables)
  is performed.
* **Per-user databases are deliberately not created at build time.** They are
  migrated lazily on first use by `ensure_user_database()`, which keeps deploys
  fast and avoids creating databases for users who never log in.
* The router's `allow_migrate` keeps `auth` / `sessions` / `admin` out of the
  guest and per-user databases.

Because Render Free instances have an ephemeral filesystem but the database is
remote, migrations run on every build/deploy and are idempotent.

## 6. Static files

WhiteNoise serves static files from `STATIC_ROOT` (`staticfiles/`).
`build.sh` runs `collectstatic --noinput`, and
`whitenoise.storage.CompressedStaticFilesStorage` pre-compresses assets.
`STATICFILES_DIRS` still points at the repository `static/` directory, so local
`runserver` keeps working unchanged.

## 7. Health and status

| Endpoint | Auth | Behaviour |
|---|---|---|
| `/health` | None | Runs `SELECT 1` against the core database. Returns `200` with `{"status": "ok"}`, or `503` with `{"status": "error"}` if the core database is unreachable. Never trains a model and never triggers fallback analysis. |
| `/status` | None | Returns runtime, database, ML and system diagnostics. Degrades to `"status": "degraded"` instead of failing when a database is unreachable. |

Both endpoints are excluded from per-request database provisioning, so Render's
polling does not issue `CREATE DATABASE` / `GRANT` statements against Aiven on
every request.

## 8. Playwright / visual analysis

Playwright is **not** installed and browser binaries are **not** downloaded.
`VisualAnalyzer` therefore returns:

```json
{"status": "UNAVAILABLE", "screenshot_reference": null,
 "error": "Playwright browser automation not installed"}
```

The Nikhil orchestrator catches this, records `UNAVAILABLE` for the `VISUAL`
evidence family, and the scan continues. Screenshot success is never faked.

If Playwright is later enabled by adding it to `requirements.txt`, the browser
binaries must additionally be installed during the build
(`python -m playwright install chromium --with-deps`). Be aware of the cost:
the Chromium download is roughly 150–250 MB, which lengthens builds
significantly and can exhaust the free instance's 512 MB of RAM while a browser
is running. **Keep the graceful `UNAVAILABLE` fallback as the default.**

## 10. Known free-tier limitations

1. **Cold starts.** Free instances sleep after ~15 minutes of inactivity; the
   first request after a wake-up takes 30–60 s while the RandomForest model is
   trained lazily.
2. **No persistent filesystem.** Screenshots and uploaded artifacts are lost on
   restart and redeploy. Only MySQL and MongoDB data persists.
3. **512 MB RAM.** The `xgboost` / `scikit-learn` / `pandas` stack plus the
   RandomForest training is memory-hungry. Use `--workers 1` to avoid memory
   duplication from multiple worker processes.
4. **~750 hours/month** of combined free usage; instances spin down outside that.
5. **No Playwright browsers** (see §8).
6. **Free Aiven plan** may throttle or drop idle connections. Aiven's free tier
   also sleeps inactive services, so the first request after a long gap can be
   slow.
7. **MongoDB Atlas free tier** requires the Render egress IP to be allowed in
   the Atlas network access list. Without it, deep analysis still completes but
   MongoDB evidence is stored only in the in-process cache.
8. **Migrations run at build time.** If the build machine cannot reach Aiven,
   the deploy fails at step 3 of `build.sh`.

## 11. Local development

Local development is unaffected. With no `MYSQL_SSL_*` variables set and
`MYSQL_HOST` pointing at localhost, TLS is skipped entirely.

```bat
.venv_canonical\Scripts\python.exe manage.py runserver
```

`start.bat` continues to work on Windows. The `.env` file is still loaded by
`MaliciousBot/settings.py` and remains git-ignored.

## 12. Verification commands

```bash
python manage.py check
python manage.py test User
python manage.py collectstatic --noinput
python manage.py makemigrations --check --dry-run   # expect: No changes detected
python manage.py showmigrations --plan
```

The deployment tests in `User/test_deployment.py` cover SSL mode selection,
`default` / `guest_db` / dynamic-user-database parity, the provisioning
connection, `/health`, `/status`, static and WhiteNoise configuration, the
free-only AI and threat-intelligence policy, and the Playwright and MongoDB
graceful-degradation paths. No real credentials are required.
