# NIKHIL — Implementation Plan & Prompts

## Project Goal
Implement the fallback/deep-analysis side of the malicious URL detection project for uncertain cases, using research-paper-inspired webpage, network, AI/LLM and flexible evidence analysis.

## Architecture We Are Building

Pari's first-stage system:

New URL
→ Random Forest / Logistic Regression
→ confidence check
→ confident → MySQL
→ uncertain → handoff to Nikhil

Nikhil's system:

UNCERTAIN
→ deep analysis
→ MongoDB flexible evidence
→ final evidence/classification
→ return structured result to Pari's MySQL layer

# PROMPT 2 — Build Modular Deep-Analysis Services

### Description
Create the actual fallback analysis modules inspired by the research papers. Keep the modules independent so one failure does not break the whole scan.

### Prompt
```text
Now implement the modular fallback/deep-analysis framework for UNCERTAIN URL cases.

The fallback must run only when the first-stage ML system marks a scan as UNCERTAIN.

Create four independent analysis modules:

1. Webpage Analysis
2. Network / Domain Analysis
3. AI / LLM Analysis
4. Additional Evidence Collection

Webpage Analysis may collect, where technically and legally appropriate:
- page title
- visible text
- HTML metadata
- forms
- suspicious elements
- JavaScript-related indicators
- redirects
- webpage structure
- screenshot or visual evidence if supported

Network / Domain Analysis may collect:
- domain information
- resolved IP address
- DNS-related information
- redirect chain
- SSL/certificate information
- shared domain/IP relationships where available
- configured threat-intelligence information

AI / LLM Analysis should be modular and designed to:
- analyze webpage text
- identify suspicious behaviour/patterns
- explain suspicious findings
- detect possible prompt-injection or malicious instructions embedded in webpage content

Additional Evidence Collection must support future evidence types without redesigning the whole service.

Requirements:
1. Each module has a clear input/output interface.
2. One module failing must not crash the entire fallback scan.
3. Record module success/failure.
4. Record timestamps.
5. Separate raw evidence from final classification.
6. Do not overwrite the original ML prediction silently.
7. Return a unified analysis object to the orchestration layer.
8. Use safe timeouts and resource limits when accessing external URLs.
9. Do not hard-code API keys or credentials.
10. Use environment variables for external integrations.

Create service interfaces such as:
- analyze_webpage(url)
- analyze_network(url)
- analyze_with_ai(data)
- collect_additional_evidence(url)

For services that require external credentials, provide a safe mock/stub mode so the application can still run locally.

Do not implement MongoDB in this step.
```

# PROMPT 3 — MongoDB Flexible Evidence Storage

### Description
Use MongoDB specifically for raw/flexible evidence generated by uncertain cases. MySQL remains the structured relational source of truth.

### Prompt
```text
Now integrate MongoDB for storing flexible/raw evidence produced by the fallback deep-analysis system.

IMPORTANT ARCHITECTURE:
- MySQL = structured relational data, relationships, history, final structured results.
- MongoDB = flexible/raw investigation evidence for UNCERTAIN cases.
- MongoDB does NOT replace MySQL.

Create a collection such as:
deep_analysis_cases

Each document must be logically linked to the corresponding MySQL scan using scan_id.

Support a flexible document shape containing sections such as:
{
  scan_id,
  url,
  analysis_status,
  webpage: {
    title,
    text,
    html,
    javascript,
    screenshot_reference,
    indicators
  },
  network: {
    domain,
    ip,
    dns,
    redirects,
    ssl,
    shared_infrastructure
  },
  ai_analysis: {
    findings,
    suspicious_patterns,
    prompt_injection_detected,
    explanation
  },
  additional_evidence: {},
  timestamps
}

Requirements:
1. Do not duplicate all relational MySQL data unnecessarily.
2. scan_id is the logical link to MySQL.
3. MongoDB must support fields that vary between investigations.
4. Store detailed/raw evidence here.
5. Keep final structured classification in MySQL.
6. Handle MongoDB failures gracefully.
7. Keep credentials in environment variables.
8. Never hard-code secrets.
9. Store references to large binary objects rather than unnecessarily embedding huge payloads.
10. Make document writes idempotent where practical.

At the end, demonstrate a sample uncertain scan where:
MySQL scan_id = 5012
and MongoDB contains the matching deep_analysis_cases document.
```

# PROMPT 4 — Final Evidence Analysis and Return Contract

### Description
Combine the fallback evidence into a final analysis output without blindly overriding the initial ML result. Return a structured result to Pari for MySQL storage.

### Prompt
```text
Now implement the final analysis/orchestration stage for UNCERTAIN cases.

Input:
- scan_id
- URL
- initial ML prediction, if available
- initial ML confidence
- results from webpage analysis
- network/domain analysis
- AI/LLM analysis
- additional evidence

Combine the available evidence into a final analysis result.

IMPORTANT:
- Do not blindly override the ML result.
- Preserve the original ML prediction and confidence.
- Make the evidence used for the final decision traceable.
- If evidence is insufficient, return Unknown / Needs Review.

Allowed final classifications:
- Benign
- Phishing
- Malware
- Defacement
- Unknown / Needs Review

Return a structured object containing at minimum:
- scan_id
- final_classification
- risk_level and/or risk_score
- evidence_summary
- threat_indicators
- analysis_status
- original_prediction
- original_confidence
- mongo_document_id/reference where available

The result must be suitable for Pari's MySQL integration layer.

Do not directly redesign Pari's MySQL schema.
Use the agreed integration contract.

Add tests covering:
1. Strong webpage evidence.
2. Strong network evidence.
3. Conflicting evidence.
4. Missing module output.
5. All modules failing.
6. Insufficient evidence → Unknown/Needs Review.
```

# PROMPT 5 — Analyst Review and Validated Learning Workflow

### Description
Provide a controlled mechanism for reviewing uncertain cases. Confirmed cases may become eligible for future retraining, but must never automatically modify the baseline training set.

### Prompt
```text
Now implement the review workflow for UNCERTAIN / UNKNOWN cases produced by the fallback system.

IMPORTANT:
Unknown cases must NOT automatically become training data.

Workflow:
UNCERTAIN
→ deep analysis
→ evidence stored in MongoDB
→ structured result sent to MySQL
→ analyst/manual review
→ confirmed classification or still unknown

Allow an authorized reviewer to assign:
- Benign
- Phishing
- Malware
- Defacement
- Still Unknown

Store review information using the project's structured database integration:
- reviewer
- reviewed_at
- final label
- review notes
- investigation reference

A reviewed case may be marked:
- VALIDATED_FOR_FUTURE_TRAINING
or
- NOT_VALIDATED

Do NOT automatically retrain the model after each review.
Do NOT automatically modify the original 400-URL baseline dataset.

Create a clean export/query mechanism for validated cases so future model retraining can happen as a deliberate separate operation.

Also expose an investigation/detail view or API that allows a reviewer to inspect available evidence before assigning the label.
```

# NIKHIL Responsibilities Summary

## Own these areas
- Fallback/deep-analysis orchestration
- Webpage analysis
- Network/domain evidence collection
- SSL/DNS/redirect evidence where available
- AI/LLM analysis module
- Prompt-injection detection within webpage content
- Flexible raw evidence handling
- MongoDB integration
- Deep-analysis result generation
- Unknown/Needs Review handling
- Analyst investigation/review workflow
- Validated-case workflow for future training eligibility

## Do NOT own
- Replacing Random Forest
- Replacing Logistic Regression
- Changing the 400-URL baseline
- Redesigning Pari's MySQL schema
- Changing the confidence threshold logic without agreement
- Automatically retraining the ML model

## Integration Contract with Pari
Receive:
- scan_id
- URL
- initial ML prediction
- initial confidence
- initial scan status
- any structured information already available

Return:
- scan_id
- final classification
- risk level/score
- evidence summary
- threat indicators
- analysis status
- MongoDB investigation document reference

## Important Safety/Engineering Rule
The fallback must treat every submitted URL as untrusted input. Use timeouts, resource limits, safe isolation where appropriate, and never execute untrusted page content as local application code.
